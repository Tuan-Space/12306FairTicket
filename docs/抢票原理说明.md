# 抢票原理说明

这份文档按代码真实执行顺序，说明本项目是如何从“启动脚本”走到“提交订单并等待结果”的。建议配合以下文件一起看：

- `main.py`
- `ticket_app/configuration.py`
- `ticket_app/clock.py`
- `ticket_app/stations.py`
- `ticket_app/client.py`
- `ticket_app/runner.py`
- `ticket_app/helpers.py`

---

## 1. 入口：`main.py`

项目入口只有一个：

```powershell
python main.py
```

`main.py` 本身不承载具体抢票细节，主要负责：

1. 解析命令行参数；
2. 加载配置；
3. 初始化日志；
4. 创建 `TicketRunner`；
5. 把控制权交给主流程。

真正的执行链路从 `TicketRunner.run()` 开始。

---

## 2. 加载配置：`ticket_app/configuration.py`

程序会先从项目根目录的 `config.py` 读取配置。这里不是读 JSON，而是把 `config.py` 当成 Python 模块导入，所以你可以直接写：

```python
FROM_STATION = "北京西"
TO_STATION = "郑州东"
PASSENGER_NAMES = ["张三"]
SEAT_TYPES = ["二等座", "无座"]
```

配置加载后会整理成 `AppConfig` 对象，并做一轮校验，包括：

- 出发站和到达站不能为空；
- 日期格式是否正确；
- 乘车人是否填写；
- 座席名称是否在支持列表中；
- 时间相关参数是否合理；
- 日志级别是否合法。

这里还定义了很多全局常量，例如：

- `BASE_URL`
- `STATION_URL`
- `SEAT_SPECS`
- `WEEKDAY_NAMES`
- `MONTH_NAMES`

其中 `SEAT_SPECS` 很关键，它决定了：

- 某种座席在余票结果里对应哪个字段；
- 某种座席提交订单时使用什么编码。

例如：

- 二等座：余票字段 `edz`，提交编码 `O`
- 一等座：余票字段 `ydz`，提交编码 `M`
- 商务座：余票字段 `swz`，提交编码 `9`

---

## 3. 初始化总控：`ticket_app/runner.py`

`TicketRunner` 是整个项目的总控类。初始化时会创建三个核心对象：

1. `RailwayClient`：负责所有和 12306 的 HTTP 请求；
2. `ServerClock`：负责与 12306 时间同步；
3. `StationStore`：负责站点编码缓存和解析。

它还会提前准备两类运行时数据：

- `preferred_order`：把 `PREFERRED_TRAINS` 转成优先级字典；
- `seat_sequence`：把 `SEAT_TYPES` 转成按顺序尝试的座席列表。

这样后面每轮查票就不用重复构建这些结构。

---

## 4. 时间同步：`ticket_app/clock.py`

项目不是按本地时间直接开始抢票，而是会先与 12306 做一次时间同步。

`ServerClock.sync()` 会：

1. 向 `https://kyfw.12306.cn/otn/leftTicket/init` 发起多次 `HEAD` 请求；
2. 从 HTTP 响应头的 `Date` 字段取服务器时间；
3. 记录每次请求的 RTT；
4. 优先选 RTT 最低的样本作为时间偏移估算依据；
5. 保存“服务器时间起点 + 单调时钟起点”。

这里的关键点是：

- 不是只同步一次，而是多次采样；
- 不是直接信任本地 `time.time()`；
- 后续等待用 `perf_counter()` 维护，减少本机时钟跳变影响。

最终 `ServerClock.now()` 返回的是“尽量接近 12306 服务器的当前时间”。

---

## 5. 站点编码：`ticket_app/stations.py`

12306 查票接口不接受“北京西”这种中文站名直接查询，而是要用站点编码。

所以程序会先请求：

```text
https://kyfw.12306.cn/otn/resources/js/framework/station_name.js
```

然后把里面的站名和编码提取出来，形成映射表，再缓存到：

```text
.runtime/stations.json
```

下次运行时，如果缓存没有过期，就直接读取，不再请求站点接口。

---

## 6. 登录状态与二维码：`ticket_app/client.py`

`RailwayClient` 内部维护一个 `requests.Session()`，这是项目所有请求共享的会话容器。

它的作用包括：

- 复用 cookie；
- 维持登录态；
- 统一请求头；
- 复用 TCP 连接。

### 6.1 先读本地登录态

程序启动后会尝试从：

```text
.runtime/session.cookies
```

读取上一次保存的 cookie。

如果 cookie 仍然有效，就可以直接跳过扫码。

### 6.2 检查当前会话是否已登录

程序会请求：

```text
/otn/login/checkUser
```

如果返回结果显示当前 session 仍然有效，就继续后面的流程。

### 6.3 会话失效时生成二维码

如果 cookie 失效，就会进入二维码登录流程：

1. 预热登录相关 cookie；
2. 请求 `/passport/web/create-qr64`；
3. 拿到 base64 二维码图片和 uuid；
4. 把二维码保存到 `.runtime/login_qr.png`；
5. 等待你用 12306 App 扫码。

### 6.4 等待扫码和登录确认

程序会循环请求：

```text
/passport/web/checkqr
```

判断二维码状态：

- 未扫码
- 已扫码未确认
- 已确认登录
- 已过期

一旦扫码成功，还会继续走：

- `/passport/web/auth/uamtk`
- `/otn/uamauthclient`

完成最终登录态建立，然后把 session cookie 再写回本地。

---

## 7. 获取乘车人：`ticket_app/client.py` + `ticket_app/runner.py`

登录成功后，程序不会要求你在本地配置身份证号和手机号，而是调用：

```text
/otn/confirmPassenger/getPassengerDTOs
```

从当前登录账号的常用乘车人列表里直接读取。

然后 `TicketRunner._select_passengers()` 会按 `PASSENGER_NAMES` 做名字匹配。如果你在配置里填了一个账号里根本没有的人，程序会直接报错并退出。

接着 `TicketRunner._prepare_passengers_by_seat_code()` 会预生成不同座席编码下的提交字符串，避免发现票以后再临时拼。

这一步会提前准备：

- `passengerTicketStr`
- `oldPassengerStr`

并按座席编码缓存起来，比如：

- `O`
- `M`
- `9`
- `1`

这样发现票后就能直接拿来下单。

---

## 8. 等待热身查询窗口：`ticket_app/runner.py`

这是当前版本中最关键的优化之一。

程序不会等到 `START_AT` 才开始第一条查票请求，而是按下面的方式处理：

1. 先算出目标开售时间 `START_AT`；
2. 再算出热身查询起点：

```text
query_start = START_AT - PRE_QUERY_SECONDS
```

3. 在这个时间点之前只等待，不查票；
4. 到了热身窗口立即进入轮询。

如果你配置：

```python
START_AT = "15:00:00"
PRE_QUERY_SECONDS = 1.5
```

那么程序会在：

```text
14:59:58.5
```

左右开始第一轮查票。

---

## 9. 查票：`ticket_app/client.py::query_tickets`

热身窗口开始后，程序会反复调用查票接口。实现上会尝试几个兼容端点：

- `/otn/leftTicket/query`
- `/otn/leftTicket/queryA`
- `/otn/leftTicket/queryZ`

提交的参数包括：

- 出发日期
- 出发站编码
- 到达站编码
- 票种（通常是成人票）

12306 返回的原始余票结果并不是结构化表，而是一串以 `|` 分隔的长字符串。所以 `_parse_tickets()` 会把每一条拆开，提取出：

- `secret_str`
- `station_train_code`
- `train_no`
- `start_time`
- `arrive_time`
- `duration`
- `date`
- `left_ticket`
- 各座席库存

其中最关键的是：

- `secret_str`：后面提交订单必须用；
- 各座席库存：决定这张票值不值得尝试。

---

## 10. 候选票筛选：`ticket_app/runner.py::_find_candidates`

查到的车次不会全部直接拿去提交，而是先按配置筛选候选票。

排序和筛选规则是：

1. 先按 `PREFERRED_TRAINS` 从左到右排序；
2. 如果 `ONLY_PREFERRED_TRAINS = True`，则只保留这些车次；
3. 再按 `SEAT_TYPES` 从左到右检查库存；
4. 有库存的组合加入候选列表。

例如：

```python
PREFERRED_TRAINS = ["G1561", "G327"]
SEAT_TYPES = ["二等座", "无座", "一等座"]
```

程序的尝试顺序会更接近：

1. `G1561 + 二等座`
2. `G1561 + 无座`
3. `G1561 + 一等座`
4. `G327 + 二等座`
5. `G327 + 无座`
6. `G327 + 一等座`

---

## 11. 真正开始抢票：`ticket_app/runner.py::_book_ticket`

只有当某次查票发现了候选票，程序才会真正进入“抢票”阶段。

这一段顺序固定如下：

### 11.1 `submitOrderRequest`

接口：

```text
/otn/leftTicket/submitOrderRequest
```

作用：

- 告诉 12306 你准备提交某趟车某天的某张票；
- 使用查票返回的 `secret_str`；
- 带上出发站、到达站、日期等信息。

### 11.2 `initDc`

接口：

```text
/otn/confirmPassenger/initDc
```

作用：

- 初始化确认订单页面；
- 从 HTML 中提取后续必须用到的隐藏参数；
- 例如：
  - `globalRepeatSubmitToken`
  - `ticketInfoForPassengerForm`

### 11.3 `checkOrderInfo`

接口：

```text
/otn/confirmPassenger/checkOrderInfo
```

作用：

- 校验乘车人信息是否有效；
- 校验票种和订单内容；
- 检查当前订单是否允许继续提交。

### 11.4 `getQueueCount`

接口：

```text
/otn/confirmPassenger/getQueueCount
```

作用：

- 获取提交确认前的系统状态；
- 确认这单还有没有继续发起的必要；
- 获取更新后的 `ticket` 等字段。

### 11.5 `confirmSingleForQueue`

接口：

```text
/otn/confirmPassenger/confirmSingleForQueue
```

作用：

- 正式把订单确认提交给 12306；
- 到这一步，通常说明这次请求已经进入结果等待阶段。

---

## 12. 等待订单结果：`queryOrderWaitTime`

订单提交之后，程序不会立刻就拿到订单号，而是会轮询：

```text
/otn/confirmPassenger/queryOrderWaitTime
```

常见情况有几种：

### 12.1 正常处理中

日志可能会出现：

```text
排队中，预计等待 4 秒
排队中，预计等待 -100 秒
```

在本项目的实测里，`-100` 不视为失败，通常仍然说明你这次提交还在 12306 的受理流程中。

### 12.2 明确失败

如果返回：

- 没有足够的票
- 余票不足
- 排队失败
- 出票失败

程序会放弃当前候选票，回到下一轮查票。

### 12.3 成功

如果返回里出现：

```text
orderId
```

说明 12306 已经生成订单。程序会打印订单号，接下来你需要自己去 12306 官方渠道付款。

## 13. 性能日志：为什么你能看到 `[PERF]`

项目里增加了性能日志，是为了回答一个很实际的问题：

> “我到底慢在了哪里？”

程序会记录这些阶段的耗时：

- 查票请求耗时
- 余票解析耗时
- 筛选候选票耗时
- 发现票到提交请求准备的耗时
- `submitOrderRequest`
- `initDc`
- `checkOrderInfo`
- `getQueueCount`
- `confirmSingleForQueue`

所以如果没有抢到票，可以先结合日志判断问题更可能出在哪里：

- 热身太晚；
- 网络 RTT 太大；
- 查票返回慢；
- 提交链路慢；
- 还是已经顺利进入系统处理流程，但 12306 最终没有放到这张票。

## 14. 模块划分：现在每个文件负责什么

### `main.py`

- 真正的项目入口
- 解析 CLI 参数
- 加载配置
- 初始化日志
- 启动 `TicketRunner`

### `ticket_app/configuration.py`

- 常量
- 配置数据类
- 配置校验
- 路径解析
- 配置加载

### `ticket_app/clock.py`

- 与 12306 时间同步
- 单调时钟等待

### `ticket_app/stations.py`

- 站点 JS 拉取
- 站点编码解析
- 本地缓存

### `ticket_app/client.py`

- 登录状态检查
- 二维码登录
- 查票
- 获取常用乘车人
- 提交订单相关全部 HTTP 请求

### `ticket_app/runner.py`

- 总控流程
- 热身窗口等待
- 候选票筛选
- 下单顺序控制

### `ticket_app/helpers.py`

- 常用字符串构造
- 失败消息判断
- JS 对象解析
- 辅助转换逻辑

## 15. 这个项目最擅长什么，不擅长什么

### 擅长

- 校准到更接近 12306 的时间
- 提前进入热身查票
- 自动读取常用乘车人
- 发现票后快速完成提交
- 在高峰期尽量抢到更靠前的提交时机

### 不擅长

- 保证一定抢到票
- 绕过 12306 配额和风控
- 决定 12306 最终把票给谁
- 自动支付

可以把这个项目的核心能力理解为：

> **尽可能快、尽可能稳地参与开售瞬间的第一波有效提交。**

至于最终出不出单，仍然受 12306 自己的放票策略、配额和结果分配影响。

---

## 16. 总结

这个项目并不会改变 12306 自身的放票规则，但它会把开售前后的关键准备动作尽量前置，把真正影响命中率的几个环节压缩到更短。

如果用一句话概括，它做的是：**提前准备，及时发现，快速提交。**
