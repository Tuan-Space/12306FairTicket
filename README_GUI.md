# 12306FairTicket 图形界面

这是原命令行抢票流程的 Windows 桌面界面。它保留服务器校时、定时热身查询、车次与席别优先级、扫码登录和订单状态轮询，并把常用设置、二维码、倒计时与运行日志集中到一个窗口中。

> 本项目使用非公开网页接口，不能保证抢票成功，也不能替代 12306 的候补、支付和订单管理。请遵守 12306 的规则，合理设置查询频率。

## 直接运行源码

推荐环境为 Windows 10/11 x64 和 Python 3.12。PowerShell 中执行：

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements-gui.txt
python gui.py
```

界面中的基础设置包括出发站、到达站、日历乘车日期、乘车人、两列可拖动的席别优先级、车次优先级、独立的时/分/秒起止时间和是否自动提交。基础页使用直接说明和控件悬停提示，避免重复的帮助图标；轮询、热身窗口、超时、校时、订单等待及日志选项位于双列高级设置中，不熟悉的技术参数可将鼠标停在 `?` 上查看默认值、合理范围和影响。

## 配置、站点与字段检查

- 顶部只有“保存为…”和“导入…”两个配置按钮，旁边会直接说明保存范围和隐私边界。保存文件固定为 `{"version": 2, "settings": {...}}`，包含界面中全部可编辑参数；导入兼容既有 version 1 JSON，但 GUI 不再导入 `config.py`。命令行入口仍可继续使用 `config.py`。
- 配置 JSON 不保存 Cookie、Token、二维码、证件信息、手机号、缓存内容、运行路径或会话策略。写入使用临时文件原子替换，未填写完整的草稿也可以保存。
- 软件刚打开时字段保持中性，不会因为尚未填写乘车人或优先车次立即标红。修改字段后约 250 ms 会检查该字段及直接依赖项；每个逻辑字段只显示一个红色轮廓和一条行内原因。“检查配置”“开始任务”和导入配置会检查全部字段，并定位到第一个错误。
- 程序启动只读取内置站点快照与 `%LOCALAPPDATA%` 缓存，不会联网。未知站名会阻止启动；只有点击“更新站点”才会在后台请求官方站点列表，失败时保留原数据。任务运行时不能更新站点。
- GUI 起止时间只表达每日 `HH:MM:SS`；勾选“立即开始”或“不设停止时间”会序列化为空字符串。命令行仍支持带日期的绝对时间。

## 登录二维码

- 每次启动应用都应使用 12306 App 扫描本次界面显示的二维码，并在手机端确认登录；不要依赖或分享上一次启动留下的二维码。
- 界面会显示二维码有效期倒计时和“等待扫码 / 已扫码待确认 / 登录成功 / 已过期”等状态。二维码过期后请在界面中刷新。
- GUI 默认使用 `persist_session=False`：不会把登录 Cookie 或二维码写入磁盘，因此每次启动都需要重新扫码。站点缓存和日志保存在 `%LOCALAPPDATA%\12306FairTicket`；参数只在你点击“保存为…”后写入所选 JSON 路径。
- `.runtime` 仅用于兼容命令行入口显式启用 `persist_session=True` 的模式；其中的 Cookie 和二维码属于敏感数据，不要上传、打包、截图分享或提交版本库。
- 程序不会在配置中要求填写身份证号或 12306 密码；乘车人信息来自扫码登录后的常用乘车人列表。

## 座位与铺位偏好

座位字母和上、中、下铺均按“软偏好”处理，而不是出票保证：

1. 在提交订单前，程序根据 `checkOrderInfo` 返回的能力判断是否能表达所选座位或铺位偏好。
2. 能力明确支持时，只提交一次带偏好的订单；如果偏好最终无法满足，由 12306 按官方逻辑随机分配。
3. 能力不支持或未知时，程序会在首次提交前移除物理位置偏好，再只提交一次由 12306 随机分配的订单。
4. 程序绝不会因位置偏好未满足而自动取消订单或重复下单。随机分配只放宽座位号/铺位限制，不会绕过已配置的乘车人、日期、车次和席别优先级。

常见动车二等座为 `A/B/C/D/F`，但一等座、商务座、卧铺动车及不同车型的布局可能不同。界面中出现某个字母不代表目标列车一定提供该位置，服务端实际支持能力始终优先。多人购票时也不保证相邻座位。

上下铺偏好仅对服务端允许选择铺位的卧铺票尝试；无座、硬座和不提供铺位选择的列车会忽略该偏好并进入随机分配。若不能接受随机位置，请不要启动自动提交。

## 倒计时与任务状态

- 开售倒计时使用程序校准后的 12306 服务器时间，而不是只看 Windows 本地时钟。
- “开始”后，网络请求在后台执行；右侧只动态显示当前所处的校时、登录、查票、提交或排队阶段，完整历史保留在底部脱敏日志中。
- 到达停止时间、最大轮次或用户取消后任务会结束。取消可能需要等待当前网络请求超时，不应通过强制结束进程来判断订单是否提交成功。
- 一旦显示订单号，请立即到官方 12306 App 的待支付订单中核对并完成支付。

确认订单页中的 `ticketInfoForPassengerForm` 由 12306 以内嵌 JavaScript 对象返回。程序先走严格 JSON 快速解析，必要时才使用安全的 JSON5 兼容解析处理单引号、未加引号的键和 JavaScript 转义；不会执行页面脚本。若响应结构仍无法识别，任务会在调用确认排队接口前安全停止，也不会继续轮番提交其他候选票。

## GUI 是否影响抢票时机

不会额外改变查询间隔或开售时刻。购票引擎、服务器单调时钟与网络请求始终在后台线程运行；倒计时定时器只负责显示。高频查询指标与日志最多每 100 ms 批量刷新，磁盘日志由独立队列线程写入，购票线程只做常量时间入队。实际网络延迟和 12306 服务端响应仍然存在，界面本身不会在请求调度中插入等待。

## 安全试用与测试边界

项目的单元测试和 GitHub Actions 只使用本地逻辑、模拟响应或构建检查，不会登录 12306，也不会提交真实订单。通过测试只说明本地代码路径符合预期，不能证明实时网页接口仍然可用。

首次使用建议关闭自动提交，仅验证以下项目：

- 站名、日期、乘车人与车次配置正确；
- 二维码显示、刷新和状态变化正常；
- 服务器时间偏移与开售倒计时合理；
- 查询日志不会出现异常高频请求。

开启自动提交前，请先检查 12306 中是否已有未完成或待支付订单。任何真实下单验证都必须由用户明确开启自动提交后自行进行，CI 和发布构建不会执行此类验证。

## 构建 Windows 目录版

先使用干净的 Python 3.12 虚拟环境安装构建依赖：

```powershell
python -m pip install -r requirements-dev.txt
.\scripts\build_windows.ps1
```

脚本会先通过 pytest（含 pytest-qt）运行全部单元与 GUI 测试，再使用 PyInstaller 生成 onedir 目录：

```text
dist\12306FairTicket\
  12306FairTicket.exe
  _internal\
  README_GUI.md
  THIRD_PARTY_NOTICES.md
```

分发和使用时必须保留整个 `12306FairTicket` 目录，不能只复制 EXE。构建脚本会用 `--noconfirm --clean` 重建同名输出；若只需在 CI 已测试后构建，可传入 `-SkipTests`。
构建完成后脚本还会以隐藏窗口运行一次 `12306FairTicket.exe --smoke-test`；只有冻结包能够正常创建并关闭主窗口时才视为构建成功，过程不会访问 12306。

GitHub Actions 工作流只运行测试、构建并上传短期 artifact，不创建标签，也不会发布 GitHub Release。第三方软件许可说明见 `THIRD_PARTY_NOTICES.md`。
