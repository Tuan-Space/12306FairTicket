# 12306FairTicket 图形界面

这是原命令行抢票流程的 Windows 桌面界面。它保留服务器校时、定时热身查询、车次与席别优先级、扫码登录和订单状态轮询，使用四个分步页面完成准备与执行。

**① 设置行程 → ② 登录并选择乘车人 → ③ 确认并开始 → ④ 等待结果**

**首次使用时前三步都是准备阶段，页面显示“任务未开始”。第 ③ 步点击“开始任务”才会执行；停止后点击“继续任务”会重新创建一轮任务。**

> 本项目使用非公开网页接口，不能保证抢票成功，也不能替代 12306 的候补、支付和订单管理。请遵守 12306 的规则，合理设置查询频率。

## 直接运行源码

推荐环境为 Windows 10/11 x64 和 Python 3.12。PowerShell 中执行：

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements-gui.txt
python gui.py
```

## 按四步完成一次任务

| 步骤 | 在本页完成 | 主操作 |
| --- | --- | --- |
| ① 设置行程 | 车站、日期、开售与停止时间、车次、席别顺序、任务模式；也可导入配置。高级参数默认折叠。 | 下一步：登录与乘车人 |
| ② 登录与乘车人 | 在账号区域扫码登录，直接勾选联系人、逐人设置车票类型；也保留手填姓名入口。 | 下一步：确认任务 |
| ③ 确认任务 | 核对完整摘要，设置座位、铺位和静音偏好。 | 开始任务 |
| ④ 等待结果 | 查看真实任务阶段、倒计时和结果；必要时停止或重新扫码恢复。 | 停止任务；停止后继续任务；成功后前往 12306 支付 |

窗口默认采用 750×880 的逻辑尺寸，按屏幕可用空间调整。顶部步骤条和页面主操作保持可见，正文可以滚动；第 ④ 页的详细日志固定在底部并默认展开，可按需收起。已访问的准备页面可以返回修改，输入会保留；“下一步”只检查当前步骤，最终开始前再完整校验。第 ③ 步就是启动确认页，点击“开始任务”后直接执行，不再重复弹出同一份确认摘要。

登录、选择乘车人、刷新联系人和校时都不会自行查票。运行中点击第 ④ 页“上一步”会立即请求停止并返回确认页，当前请求结束及后台清理完成前，配置保持只读。停止完成后可修改配置并在确认页重新开始；若无需修改，也可在结果页点击“继续任务”，按当前配置重新创建一轮任务，查询计数从 0 开始。停止保留草稿、仍有效的会话和成功的校时结果；“继续任务”不会接续上一轮的查询轮次或候选队列。

轮询、热身窗口、超时、校时、订单等待及日志选项位于第 ① 步的高级参数中。详细操作见 [四步订票流程操作说明](docs/四步订票流程操作说明.md)。

## 车次范围与尝试顺序

界面会识别 `G/D/C` 高铁/动车、其他合法车次（包括纯数字车次）及混合输入，并显示实际尝试范围。坐席、卧铺两个菜单默认展开，手动收起后不会随车次变化重新展开。输入未完成或格式错误时保留原设置并提示修正；不会自动勾选、删除或重排席别。动车也可能有卧铺，具体能否选座、选铺仍以当前订单的服务端能力为准。

- **有优先车次**：勾选“只尝试上述车次”就严格限定清单；未勾选则允许其他所有类型列车备选。实际订票仍须满足已选席别。
- **未指定车次**：不限列车类型，只按已勾选席别筛选；不再显示额外范围选项。清空车次会同时取消“只尝试上述车次”。导入的旧配置如果清单为空却启用了该限制，会保留错误，需明确取消限制或补填车次。
- **席别选择**：新打开程序不预选任何席别，至少选一种才能启动。两个可折叠菜单均每行三列：“坐席”包含商务座、特等座、一等座、二等座、软座、硬座、无座；“卧铺”包含高级软卧、软卧、硬卧、一等卧、二等卧。下方“已选席别与优先顺序”同样三列，可拖动排序，也可点击或按空格取消。导入配置会恢复保存的选择和顺序。
- **尝试策略菜单**：右侧的向下箭头表示可展开，点击箭头或文字区域均可打开，也支持 Alt+↓ 及方向键、回车选择。
- **车次优先（默认）**：对每个优先车次依次尝试所选席别，再尝试其他允许的车次。
- **席别优先**：先尝试所有允许车次的首选席别，再尝试下一席别；同一席别内，填写的优先车次在前，其余按车次编号排序。

例如车次 `G123 → G125`、席别 `二等座 → 一等座`，限定上述车次时，“车次优先”为 `G123 二等座 → G123 一等座 → G125 二等座 → G125 一等座`；“席别优先”为 `G123 二等座 → G125 二等座 → G123 一等座 → G125 一等座`。界面顺序是示例，实际执行会跳过无票候选。

命令行可在 `config.py` 设置 `PRIORITY_STRATEGY = "train_first"` 或 `"seat_first"`；CLI 仍支持 `EMPTY_TRAIN_SCOPE = "high_speed"`、`"conventional"` 或 `"all"`，仅在优先车次为空时生效。未配置时分别默认 `train_first` 和 `all`。GUI 构建任务及保存配置时，兼容范围字段始终写为 `all`。

## 配置、站点与字段检查

- 乘车人与优先车次支持中英文逗号（`,`、`，`）、顿号（`、`）、中英文分号（`;`、`；`）、换行和制表符分隔，可以混用；连续及首尾多余分隔符会自动忽略。示例：`张三，李四、王五`、`g79；G95, D123`。姓名内部空格会保留，重复乘车人会提示错误，每次最多 5 人；车次统一转为大写并保留输入顺序。现有配置 JSON 数组格式继续兼容，建议每名乘车人和每个车次分别保存为一个数组项。
- 顶部只有“保存为…”和“导入…”两个配置按钮。保存文件为 `{"version": 4, "settings": {...}}`，包含全部可编辑参数；支持导入 version 1、2、3、4 JSON。旧版配置保留车次、席别顺序及偏好，车票类型默认按 12306 乘客信息、静音偏好默认关闭。旧预览版的范围限制会转换为不限类型，并在导入提示中说明；未选席别的草稿也可以保存。旧软件不能读取 v4 配置，避免忽略车票类型设置后意外购买学生票。GUI 不导入 `config.py`，命令行入口仍可使用。
- 配置 JSON 不保存 Cookie、Token、二维码、证件信息、手机号、缓存内容、运行路径、会话策略或向导进度。写入使用临时文件原子替换，未填写完整的草稿也可以保存。导入不会恢复登录状态，也不会自行开始任务。
- 软件刚打开时字段保持中性，不会因为尚未填写乘车人或优先车次立即标红。修改字段后约 250 ms 会检查该字段及直接依赖项；每个逻辑字段只显示一个红色轮廓和一条行内原因。“下一步”检查当前步骤；最终“开始任务”会检查全部字段，并定位到错误所属页面和字段。返回修改人数或席别时，会重新检查相关位置偏好。
- 程序启动只读取内置站点快照与 `%LOCALAPPDATA%` 缓存，不会联网。未知站名会阻止启动；只有点击“更新站点”才会在后台请求官方站点列表，失败时保留原数据。任务运行时不能更新站点。
- GUI 起止时间只表达每日 `HH:MM:SS`；勾选“立即开始”或“不设停止时间”会序列化为空字符串。命令行仍支持带日期的绝对时间。

## 乘车人与成人／学生票

第 ② 步的账号区域提供统一的“扫码登录 12306”入口，底部可返回“上一步”，登录后显示“下一步：确认任务”；准备页无需先点击登录检查。使用 12306 App 扫码并确认后，页面显示已登录，同一区域自动读取并显示联系人列表。直接勾选最多 5 人，按选择先后保留顺序；也可切换到手工填写姓名。完成后点击“下一步：确认任务”继续。无需再打开独立的联系人选择弹窗。

“重新读取”只刷新联系人数据，不启动订票，也不隐式触发扫码。会话明确失效时，本页会提示重新登录。若已经登录但联系人读取失败，会保持“已登录”状态，并提供重新读取和手动填写姓名；读取失败不等于登录失败。

每位乘车人都有“默认（按12306乘客信息）／成人票／学生票”选项。读取到成人或学生联系人身份后，默认项会明确显示“默认（12306：成人票）”或“默认（12306：学生票）”。学生联系人购买成人票时只改变本次车票类型，不改变账号内的联系人身份。同一订单允许成人与学生混合；非学生联系人不能直接指定学生票，学生资质与优惠次数仍由 12306 审核。程序不会因为学生票被拒绝就自动按成人票重订。

同名联系人、找不到联系人或超过 5 人均会明确提示。GUI 只保存姓名与车票类型映射，身份证、手机号等原始联系人字段不会写入配置。

CLI 对应示例：`PASSENGER_TICKET_TYPES = {"张三": "adult", "李四": "student"}`。映射中未指定的姓名沿用联系人类型。

## 登录二维码与手动检查

- 每次启动应用后，在第 ② 步使用 12306 App 扫描本次界面显示的二维码，并在手机端确认登录；不要依赖或分享上一次启动留下的二维码。登录成功不会开始订票。
- 同一次打开应用期间，停止任务、修改配置后可再次开始。仍有效的会话可继续使用；需要认证时，第 ② 步明确显示扫码入口。
- 界面会显示二维码有效期倒计时和“等待扫码 / 已扫码待确认 / 登录成功 / 已过期”等状态。二维码过期后请在界面中刷新。
- GUI 默认使用 `persist_session=False`：不会把登录 Cookie 或二维码写入磁盘，因此每次启动都需要重新扫码。站点缓存和日志保存在 `%LOCALAPPDATA%\12306FairTicket`；参数只在你点击“保存为…”后写入所选 JSON 路径。
- `.runtime` 仅用于兼容命令行入口显式启用 `persist_session=True` 的模式；其中的 Cookie 和二维码属于敏感数据，不要上传、打包、截图分享或提交版本库。
- 程序不会在配置中要求填写身份证号或 12306 密码；乘车人信息来自扫码登录后的常用乘车人列表。

准备页不显示“检查登录状态”，直接使用账号区域的登录入口。运行页等待开售时可手动检查会话，结果注明检查时间：检查时已登录、未登录／已失效或检查失败。网络故障、异常页面和缺少状态字段属于检查失败，不会被误报为登录失效，也不会清除 Cookie。

等待任务若明确查到会话失效，会留在第 ④ 页，显示“当前任务等待重新登录，扫码后自动继续”并展开恢复二维码。重新扫码成功后重新加载、匹配乘车人并恢复原目标时间，**无需再次点击“开始任务”**。二维码过期时可刷新或停止，任务保持暂停。手动检查失败保留已有会话与等待状态；自动复查失败则结束任务并提示重新开始。

## 定时复查与校准时间

定时任务在启动准备后，通常于开售前 **3 分钟**复查一次登录、前 **1 分钟**执行最终校时。若不足 3 分钟才完成初次登录，不紧接着重复检查；如果登录完成时已过最终校时时点，则立即补校时。重新扫码可能切换账号，因此必须重新匹配乘车人后才会继续。

“校准时间”位于时间设置和运行页的辅助区域，可在空闲或等待时测量当前 RTT，并显示时钟偏移和校准时间。准备阶段校时结束仍保持“任务未开始”；等待中校时完成后恢复等待。手动请求与其他网络操作串行处理；检查、校时执行中禁止重复点击。登录、查票及下单时两个手动按钮停用，避免插入额外请求。

校时沿用配置中的采样数量，采用符合 RTT 阈值的最低延迟样本（没有符合阈值的样本时采用总体最低值）。额外校时使用 10 秒采样预算，请求超时受剩余预算约束；网络请求仍可能受系统调度等因素影响。新一轮失败会保留上次成功的校时结果并标明失败，只有从未成功校时时才回退到本地时间。

已有提前热身秒数不变。对于较长热身设置，设热身时点为 `H`，校时点为 `min(开售−60秒, H−10秒)`，复查点为 `min(开售−180秒, 校时点−120秒)`，确保维护操作安排在热身前。登录完成过晚时，完成校时后立即查票；查票和下单期间不追加周期性或逐候选登录检查。

## 座位与铺位偏好

先在第 ① 步选择需要购买的席别：点击复选框、席别文字或该项内空白均可勾选/取消，键盘空格也可切换；拖动只调整优先级，不改变勾选状态。第 ② 步确定乘车人数后，在第 ③ 步设置座位、铺位和静音偏好。

设置上、中、下铺数量前，需要至少勾选五种卧铺席别中的一种。“去选择卧铺席别”会返回席别所在的准备页，不自动添加席别。启用时，各铺位数量之和须等于乘车人数。取消全部卧铺席别后，已填写数量保留为“未启用”，不会校验数量或提交；重新勾选卧铺后恢复校验，也可以清空。

只有支持 ABCDF 的座席才显示可操作的座位图，硬座、软座、无座不会启用它。取消全部适用座席时，座位关系同样保留为可清空的未启用草稿。座卧混选时，两项偏好分别作用于对应候选；正常的不适用情况不再产生“降级”警告。服务端未开放实际请求的偏好时，仍会明确提示系统分配。

座位字母和上、中、下铺均按“软偏好”处理，而不是出票保证：

1. 在提交订单前，程序根据 `checkOrderInfo` 返回的能力判断是否能表达所选座位或铺位偏好。
2. 能力明确支持时，只提交一次带偏好的订单；如果偏好最终无法满足，由 12306 按官方逻辑随机分配。
3. 能力不支持或未知时，程序会在首次提交前移除物理位置偏好，再只提交一次由 12306 随机分配的订单。
4. 程序绝不会因位置偏好未满足而自动取消订单或重复下单。随机分配只放宽座位号/铺位限制，不会绕过已配置的乘车人、日期、车次和席别优先级。

常见动车二等座为 `A/B/C/D/F`，但一等座、商务座、卧铺动车及不同车型的布局可能不同。界面中出现某个字母不代表目标列车一定提供该位置，服务端实际支持能力始终优先。多人购票时也不保证相邻座位。

上下铺偏好仅对服务端允许选择铺位的卧铺票尝试；无座、硬座和不提供铺位选择的列车会忽略该偏好并进入随机分配。若不能接受随机位置，请不要启动自动提交。

一等卧、二等卧分别使用独立席别代码 `I`、`J`，与软卧 `4`、硬卧 `3` 分开选择。程序依据查询返回的席别代码区分共用余票列，不按车次前缀猜测；代码缺失或无法区分时跳过该卧铺候选，并在日志中去重提示。

“静音车厢偏好”默认关闭，适用于本次全部乘车人。只有实际二等座候选且 12306 返回的数据明确开放静音能力时，才会向最终确认请求提交 `is_jy=Y`；无座即使复用二等座提交码也不启用。能力缺失、不支持或其他席别时保留设置但不启用，并在日志中说明。它可以与座位关系偏好一起使用，不保证分配到静音车厢，也不触发取消重订。CLI 对应 `QUIET_CARRIAGE_PREFERENCE = True`。

启用静音偏好前应了解：全部同行乘车人需保持安静、设备静音、不外放，到车厢外接打电话或交谈，并照看儿童；携婴幼儿者不建议选择。

## 倒计时与任务状态

- 所有 Windows 系统通知和提示音均已关闭；请查看程序内状态、日志及成功／失败提示框。
- 开售倒计时使用程序校准后的 12306 服务器时间，而不是只看 Windows 本地时钟。
- 第 ③ 步点击“开始任务”后进入第 ④ 步，网络请求在后台执行；页面显示正在准备、等待开售、查票、提交、排队或最终结果等真实阶段。准备页不显示运行时间线和大号倒计时。
- 第 ④ 页的详细日志固定在窗口底部，默认展开，可按需收起；错误摘要和任务结果始终可见。扫码登录或校时等准备操作不会把界面显示为正在抢票。
- 到达停止时间、最大轮次或用户取消后任务会结束。取消可能需要等待当前网络请求超时，不应通过强制结束进程来判断订单是否提交成功。
- 一旦显示订单号，请立即到官方 12306 App 的待支付订单中核对并完成支付。

确认订单页中的 `ticketInfoForPassengerForm` 由 12306 以内嵌 JavaScript 对象返回。程序先走严格 JSON 快速解析，必要时才使用安全的 JSON5 兼容解析处理单引号、未加引号的键和 JavaScript 转义；不会执行页面脚本。若响应结构仍无法识别，任务会在调用确认排队接口前安全停止，也不会继续轮番提交其他候选票。

订单接口返回无法解析的 JSON 时，诊断记录包括状态码、响应类型、重定向情况和响应长度，不记录响应正文、Cookie 或票据凭据。此类错误不等于一定登录失效；订单状态无法确认时仍会停止，请前往官方订单页核对。

## GUI 是否影响抢票时机

不会额外改变查询间隔或开售时刻。购票引擎、服务器单调时钟与网络请求始终在后台线程运行；倒计时定时器只负责显示。高频查询指标与日志最多每 100 ms 批量刷新，磁盘日志由独立队列线程写入，购票线程只做常量时间入队。实际网络延迟和 12306 服务端响应仍然存在，界面本身不会在请求调度中插入等待。

## 安全试用与测试边界

项目的单元测试和 GitHub Actions 只使用本地逻辑、模拟响应或构建检查，不会登录 12306，也不会提交真实订单。通过测试只说明本地代码路径符合预期，不能证明实时网页接口仍然可用。

首次使用建议关闭自动提交，仅验证以下项目：

- 站名、日期、乘车人与车次配置正确；
- 二维码显示、刷新和状态变化正常；
- 服务器时间偏移与开售倒计时合理；
- 查询日志不会出现异常高频请求。

开启自动提交前，请先检查 12306 中是否已有未完成或待支付订单。任何真实下单验证都必须由用户明确开启自动提交后自行进行，CI 和发布构建不会执行此类验证。

## 构建 Windows 目录版

先使用干净的 Python 3.12 虚拟环境安装构建依赖：

```powershell
python -m pip install -r requirements-dev.txt
.\scripts\build_windows.ps1
```

脚本会先通过 pytest（含 pytest-qt）运行全部单元与 GUI 测试，再使用 PyInstaller 生成 onedir 目录：

```text
dist\12306FairTicket\
  12306FairTicket.exe
  _internal\
  README_GUI.md
  THIRD_PARTY_NOTICES.md
```

分发和使用时必须保留整个 `12306FairTicket` 目录，不能只复制 EXE。构建脚本会用 `--noconfirm --clean` 重建同名输出；若只需在 CI 已测试后构建，可传入 `-SkipTests`。
构建完成后脚本还会以隐藏窗口运行一次 `12306FairTicket.exe --smoke-test`；只有冻结包能够正常创建并关闭主窗口时才视为构建成功，过程不会访问 12306。

GitHub Actions 工作流只运行测试、构建并上传短期 artifact，不创建标签，也不会发布 GitHub Release。第三方软件许可说明见 `THIRD_PARTY_NOTICES.md`。
